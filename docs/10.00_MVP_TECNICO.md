# DONATION
## 10.00 — MVP técnico: confirmación de voluntarios (Misión Levantar Chocó)

**Versión:** 0.1
**Estado:** Implementado (primera iteración)
**Fecha:** Septiembre 2026
**Alcance:** módulo 07 — Voluntarios y módulo 08 — Misiones (subconjunto operativo para la primera misión)

---

## 1. Qué resuelve esta iteración

La primera misión de campo (9–12 de octubre de 2026) necesita confirmar a **40 personas** de Grupo Kairós y Fundación Pálpitos y tener su información logística lista antes del despliegue. Esta iteración entrega:

1. **Formulario público de confirmación** (`/misiones/<slug>/confirmar`), pensado para celular, que recoge: participación (confirmo / no seguro / no puedo), disponibilidad, transporte, rol preferido, datos personales, documento, EPS, RH, contacto de emergencia, condiciones médicas, alimentación, habilidades, talla y consentimiento de datos (Ley 1581 de 2012).
2. **Control de cupos**: cuando se llenan los cupos, las nuevas confirmaciones entran a lista de espera automáticamente.
3. **Sin duplicados**: una persona se identifica por tipo + número de documento. Si vuelve a enviar el formulario, su registro se actualiza en vez de duplicarse.
4. **Panel del equipo** (`/admin`, protegido con contraseña): cupos, confirmados, lista de espera, pendientes y cancelados por misión; desglose por grupo, rol y logística; lista de participantes con búsqueda y filtros; ficha de cada persona con cambio de estado, rol asignado y notas internas; historial de cambios; exportación CSV para Excel; enlace del formulario listo para compartir por WhatsApp.
5. **Multi-misión desde el día uno**: el panel permite crear y editar misiones (nombre, fechas, cupos, apertura/cierre de inscripciones).
6. **Usuarios y roles**: cada miembro del equipo entra con su correo y contraseña propia. Tres roles: administrador, coordinador de misión y solo consulta. Los administradores crean cuentas con contraseña temporal (obligatorio cambiarla al entrar), las desactivan y las restablecen. Los datos de salud y contacto de emergencia solo los ven administradores y coordinadores.
7. **Condiciones de participación (consentimiento informado)**: cada misión puede tener un documento en Markdown, una lista de casillas de aceptación y una versión. Tras confirmar, la persona pasa al "Paso 2": lee el documento completo, marca todas las casillas, responde si autoriza el uso de su imagen, y firma escribiendo su nombre tal como lo registró y su ciudad. Queda registrada la fecha y hora, la versión, una huella (SHA-256) del texto exacto aceptado y el navegador usado. Si la versión sube, la aceptación anterior deja de valer y se pide de nuevo. El panel muestra quién aceptó, permite copiar o enviar por WhatsApp el enlace personal de aceptación, filtra "condiciones pendientes" y lo exporta en el CSV.
8. **Aporte económico**: la misión puede indicar el aporte por persona (informativo en el formulario). El equipo marca en cada ficha el estado del aporte (pendiente, pagado, parcial, exento), el valor recibido y una referencia. El panel muestra "aporte pagado X/N confirmados" y filtra "aporte pendiente".
9. **Requisitos de viaje** en el formulario: parentesco y segundo teléfono del contacto de emergencia, fecha de la vacuna contra la fiebre amarilla y póliza de accidentes. Se ven en la ficha (quien puede ver datos sensibles) y en el CSV.
10. **Consola de coordinación** (diseño del prototipo "Misión Chocó · Coordinación"): barra lateral con la misión, navegación (Resumen, Voluntarios, Tareas, Coordinación) y la lista de coordinadores por área; **Centro de misión** con fase actual, días a la salida, criterios Go / No-Go, tarjetas por área con avance y "siguiente tarea", pendientes críticos y actividad; **Coordinación por áreas** (Logística, Transporte, Alimentación, Financiero, Espiritual, Emocional) con el coordinador, sus tareas, el equipo de voluntarios del área y contacto por WhatsApp; **Tablero de tareas** (pendiente → en curso → hecha).
11. **Tareas**: por misión y área, con responsable, fecha límite, estado y marca "Criterio Go / No-Go". La misión inicial trae 40 tareas tomadas del Master Plan (§3 y §21).

## 2. Qué NO incluye (a propósito)

Siguiendo el principio "no desarrollar funcionalidades que no sean necesarias para operar la primera misión" (00.01 §9): familias, viviendas, donaciones, finanzas, inventario, evidencias e impacto quedan para las siguientes iteraciones. El esquema de datos está pensado para agregarlas sin rehacer lo existente.

## 3. Arquitectura

| Capa | Decisión | Por qué |
|---|---|---|
| Framework | Next.js 16 (App Router, Server Actions) | Una sola base de código para formulario público y panel; despliegue directo en Vercel. |
| Estilos | Tailwind CSS 4 | Rapidez y consistencia visual; móvil primero. |
| Base de datos | SQLite/libSQL vía Drizzle ORM. Local: archivo `data/donation.db`. Producción: Turso. | Cero configuración en desarrollo; en producción un servicio gestionado con capa gratuita suficiente para esta etapa. |
| Migraciones | SQL versionado en `src/lib/db/migrations.ts`, aplicado al arrancar | Sin pasos manuales de despliegue; idempotente. |
| Autenticación | Usuarios en base de datos (correo + contraseña con scrypt) y cookie firmada (HMAC) con la fecha de emisión; cambiar la contraseña invalida sesiones anteriores | Sin dependencias externas; cada acción del equipo queda atribuida a una persona. |
| Autorización | Matriz de permisos por rol y alcance (grupo o área) en `src/lib/permissions.ts`; cada página y acción del panel exige el permiso en el servidor | La interfaz esconde botones, pero la seguridad no depende de ella. |
| Diseño | Tokens en `src/app/globals.css` (paleta verde/crema, Schibsted Grotesk + JetBrains Mono), consola en `src/components/admin-shell.tsx` | Sigue el prototipo de coordinación; una sola fuente para colores y componentes. |
| Validación | zod, en el servidor | Toda acción valida la entrada aunque el navegador la omita. |
| Trazabilidad | Tabla `activity_log` | Cada inscripción y cada cambio administrativo deja rastro (principio 4.2). |

## 4. Modelo de datos

```text
organizations        grupos aliados (Grupo Kairós, Fundación Pálpitos, ...)
missions             misiones de campo (código, slug, fechas, cupos, estado, inscripciones abiertas)
volunteers           personas (únicas por tipo + número de documento)
mission_registrations inscripción de una persona a una misión (estado, respuesta, logística, rol, notas)
users                usuarios del panel (correo, hash, rol, alcance: organización o área, teléfono, activo, contraseña temporal)
tasks                tareas por misión y área (responsable, fecha límite, estado, criterio Go/No-Go)
terms_acceptances    aceptación de condiciones (inscripción, versión, huella del texto, casillas, imagen, firma, fecha)
activity_log         bitácora de cambios (actor = nombre del usuario, 'publico' o 'sistema')
```

La misión guarda además: `contribution_amount` (aporte), `terms_markdown`, `terms_declarations` (una casilla por línea), `terms_version` y `terms_image_consent`. La inscripción guarda `payment_status`, `payment_amount` y `payment_notes`.

Roles y permisos:

| Permiso | Administrador | Líder de grupo | Coordinador de área | Solo consulta |
|---|:-:|:-:|:-:|:-:|
| Ver panel, listas y fichas | ✓ | ✓ (su grupo) | ✓ | ✓ |
| Gestionar participantes (estado, rol, notas, contacto, aporte) | ✓ | ✓ (su grupo) | | |
| Ver salud, EPS, RH, vacuna, póliza y contacto de emergencia | ✓ | ✓ (su grupo) | solo Logística | |
| Exportar CSV | ✓ | ✓ (su grupo) | | |
| Crear tareas | ✓ (cualquier área) | ✓ (propias) | ✓ (su área) | |
| Editar, avanzar o cerrar tareas | ✓ | las propias | las de su área o propias | |
| Crear y editar misiones | ✓ | | | |
| Gestionar usuarios | ✓ | | | |

Grupos hoy: Grupo Kairós y Fundación Pálpitos (un líder por grupo). Áreas: Logística, Transporte, Alimentación, Financiero, Acompañamiento espiritual y Acompañamiento emocional (un coordinador por área). Un usuario lleva su alcance (`organization_id` o `area`).

Rutas del panel: `/admin/m/<misión>` (centro de misión), `/voluntarios`, `/voluntarios/<inscripción>`, `/tareas`, `/tareas/<tarea>`, `/areas/<área>`, `/editar`, `/export`; globales: `/admin/misiones`, `/admin/usuarios`, `/admin/cuenta`. Las rutas anteriores redirigen.

Estados de una inscripción: `confirmado` · `lista_espera` · `pendiente` · `cancelado`.
Estados del aporte: `pendiente` · `pagado` · `parcial` · `exento`.

Flujo de la persona voluntaria:

```text
FORMULARIO DE CONFIRMACIÓN  →  CUPO (confirmado / lista de espera)  →  PASO 2: CONDICIONES DE PARTICIPACIÓN  →  APORTE (lo marca el equipo)
```

## 4b. Despliegue

Producción en Vercel: proyecto `donation`, <https://donation-psi-tawny.vercel.app>, conectado al repositorio por la integración de GitHub (cada push a `claude/stoic-mayer-8o32sp` despliega solo). Base de datos en Turso (store del Marketplace de Vercel, conectado en los tres entornos). La autenticación de Vercel solo protege previews; producción es pública. Si no hay ninguna variable con URL `libsql://` y `ALLOW_EPHEMERAL_DB=true`, corre en modo demostración (base temporal en `/tmp`, formulario público cerrado, aviso en el panel); el administrador ve en la barra lateral qué base usa el despliegue. Variables necesarias en producción: `AUTH_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`; opcional `ADMIN_NAME`, `NEXT_PUBLIC_SITE_URL`. `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` evita que la instalación descargue navegadores en el build.
